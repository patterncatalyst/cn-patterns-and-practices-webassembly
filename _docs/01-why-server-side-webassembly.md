## Learning objectives

By the end of this chapter you can:

- Explain what a Wasm component adds on top of a `.wasm` module (a typed interface instead of raw linear-memory pointers) and why that matters for a server workload, not just a browser one.
- Compare a Wasm component against a container on cold-start time, image size, and the isolation mechanism each one relies on.
- Name the cases where server-side Wasm does not win: heavy native dependencies, long-lived stateful processes, and workloads that need a full POSIX surface.
- Describe the one WIT contract this site builds against, in both Rust and Go, and the two runtimes (wasmtime and wasmCloud) it runs under.

## Why this matters

A container solved real problems (packaging, isolation, portability), and most server workloads still reach for one by default, the same way the REST and gRPC sibling sites reach for HTTP and Protobuf without asking what else might answer the same need. This chapter asks that question of the container directly. A Wasm component starts in single-digit milliseconds, ships as a single-digit-megabyte artifact, and runs inside a sandbox that denies every syscall unless the host explicitly grants it. None of that makes it a replacement for the container: a component with no access to a POSIX filesystem can't shell out to a legacy binary, and a hand-rolled C library with no path through WASI stays off this site entirely. What follows is the comparison itself, concrete enough that every later chapter's decision to use a component, or not to, traces back to something specific here.

## What a component is, briefly

A `.wasm` module is a compiled unit of code: a flat block of linear memory, a table of functions, and nothing describing what those functions mean to anyone outside the module. Two modules compiled from different languages that want to call each other have to agree, by hand, on how integers and pointers into that memory line up. That's brittle in a browser, where the module usually talks to a single JavaScript host, and much more brittle on a server, where the whole point is many components written in different languages calling each other's interfaces.

The **Component Model** replaces that hand-rolled agreement with a typed interface described once, in the WebAssembly Interface Type language (WIT), and compiled into bindings for whichever language a component is written in. A WIT interface declares records, enums, resources, and functions with real types (strings, lists, options, results), not raw bytes. Two components built from the same WIT world, one in Rust and one in Go, call each other's exported functions without either side knowing or caring what language wrote the other. That's the shape this site's shared cargo domain takes: one `cargo` world, implemented once in Rust and once in Go, each a drop-in replacement for the other because both compile against the same `patterncatalyst:cargo` package.

As of 2026-10, the Component Model itself is pre-1.0 (it's in W3C Phase 2/3), and the surrounding toolchain has caught up enough to build real things against it: wasmtime 50.0.0 implements the model fully, `cargo-component` 0.21.1 generates Rust bindings from WIT directly, and Rust 1.99.1 stable can target `wasm32-wasip2` without a nightly toolchain. WASI Preview 2 (the 0.2.x line) is the current stable target for host interfaces, including filesystem, sockets, and clocks, that a component imports instead of calling the OS directly. None of that means the ecosystem has stopped moving; it means there's finally enough here to build server workloads on, which is what makes this a reasonable year to start.

## The case for server-side Wasm

Three properties make a Wasm component worth the comparison against a container at all: startup time, density, and the shape of its default isolation.

**Cold start** is the most visible difference. A container's cold start pays for process creation, cgroup and namespace setup, and whatever the application's own runtime needs to initialize: a JVM warming up its JIT, a Python interpreter importing modules, a Node process parsing and compiling JavaScript. That adds up to hundreds of milliseconds at best, seconds at worst, which is tolerable for a pod that runs for hours but expensive for a function that exists to handle one request and exit. A Wasm component under wasmtime skips almost all of that: the module is already compiled (ahead-of-time or cached after a first JIT pass), instantiation is allocating linear memory and wiring up imports, and the whole thing is measured in single-digit milliseconds. That gap is what makes scale-to-zero a realistic default instead of a workaround for slow starts, and it's the reason a Wasm sidecar can spin up per-request without the caller noticing.

**Density** follows from the same mechanics. A container's isolation boundary is the kernel: each one gets its own network namespace, mount namespace, and cgroup, overhead that's fixed per container regardless of how little work it does. A wasmtime host can run hundreds of component instances in the memory footprint of a handful of containers, because an instance is closer to a heap allocation than a process. That changes the economics of a workload with many small, short-lived units of logic, such as a per-tenant policy check or a per-request transform, where a container-per-unit design would spend more on isolation overhead than on the work itself.

**Isolation** is the property that's easiest to misstate, so it's worth being precise. A container is isolated by the kernel: namespaces hide most of the host's process tree, filesystem, and network stack from what's inside, and cgroups cap what it can consume, but a container still makes real syscalls into a kernel it shares with the host and with every other container on the node: a kernel vulnerability or a syscall-level escape reaches further than the pod boundary. A Wasm component, by contrast, has no ambient authority to the host at all. It cannot open a file, open a socket, or read the clock unless the host embedding it explicitly wires that capability in through WASI. That's deny-by-default, where a container is closer to allow-by-default-minus-namespacing. That's a narrower default blast radius for code you don't fully trust: a third-party plugin, a user-submitted transform, a dependency with a known CVE that you can't patch today but can at least contain. The execution model's linear-memory sandbox, covered next, builds directly on this claim; this chapter only establishes that the claim is real and why it follows from the sandbox's construction, not from a vendor's marketing.

**Portability** rounds out the pitch, though it's the softest of the four. A `.wasm` component compiled once runs unmodified under wasmtime on Linux, macOS, or Windows, and under wasmCloud distributed across however many hosts are in the lattice: no `GOOS`/`GOARCH` matrix, no separate container image per architecture. A container image still needs a base image matching the target CPU architecture and, practically, the target OS family; a Wasm component needs neither, because the bytecode itself is the portable unit and the host supplies everything else through the capabilities it grants. That portability is also why this site deploys the same component unmodified to both minikube and OpenShift Local (CRC) in Part 5: the component doesn't change between clusters, only the host's capability grants do.

**Polyglot composition** is the property unique to the Component Model rather than to Wasm generally. A `.wasm` module compiled from C and one compiled from Rust could always, in principle, be linked at the binary level, but nothing enforced that their function signatures agreed on meaning rather than just byte layout. A WIT world removes that ambiguity: the Rust cargo component and the Go cargo component in this site's examples both implement the same `cargo` world, and a third component written in any language with a WIT toolchain (C, JavaScript via `componentize-js`, Python via `componentize-py`) could implement it too, without either existing component changing. Containers achieve a coarser version of language-agnosticism (each container can run anything), but composition between two containers is still a network call across process boundaries, not an in-process typed function call the way two linked components can be.

## Where it does not win

None of the four properties above make server-side Wasm a universal replacement for a container, and the chapters that follow lean on specific limits more than they lean on the pitch.

**Heavy native dependencies** are the sharpest limit. A service that links against a mature native library (a GPU-accelerated inference library, a decades-old C image codec, an ODBC driver with no portable equivalent) usually has no path to a `wasm32-wasip2` target at all, because that library was never built with WASI's capability model in mind and porting it is not a weekend's work. A container happily runs that same native binary unmodified. This site's wasi-nn coverage touches portable inference specifically because it's one of the few native-dependency-heavy domains with an emerging WASI story; it is the exception, not evidence that the general problem is solved.

**Long-lived stateful processes** fit a container's model better than a component's. A component instance is cheap to create and cheap to discard, which is exactly backwards from what a process holding a large in-memory cache, a long database connection pool, or gigabytes of warmed-up state wants. Rebuilding that state on every cold instantiation defeats the reason the state existed. wasmCloud's actor model manages instance lifetime with more structure than a bare wasmtime embedding does, but even there, a workload whose whole value is a long-lived process is a container workload first.

**A full POSIX surface** is the third limit, and it's the one most likely to surprise someone used to containers. WASI Preview 2 exposes files, sockets, clocks, and a few other host facilities as explicit, capability-gated interfaces: not `fork()`, not signals, not `ptrace`, not arbitrary `ioctl` calls, not a real process table to inspect. Software written assuming POSIX is fully present (a shell script, a tool that forks subprocesses, anything doing raw device access) doesn't compile to a component today, and some of it may never need to, because the sandbox's whole value proposition depends on not handing out that authority by default.

Table 1.1 makes the comparison concrete with the numbers this chapter has been building toward, each one representative rather than a benchmark run against a specific workload:

| | Container (OCI image) | Wasm component (wasmtime) |
|---|---|---|
| Typical image size | Tens to hundreds of MBs | Single-digit MBs |
| Cold start | Hundreds of ms to low seconds | Single-digit to low tens of ms |
| Isolation mechanism | Kernel namespaces + cgroups, shared kernel | Runtime sandbox, capability-gated host calls |
| Default host access | Namespaced but broad (syscalls reach the shared kernel) | None; explicit grants only (WASI) |
| Cross-platform artifact | One image per OS/arch combination | One `.wasm` binary, any host with a compliant runtime |
| Long-lived state | Natural fit (persistent process) | Awkward (instances are meant to be cheap and short-lived) |
| Native library support | Full (whatever the base image ships) | Limited to what compiles to `wasm32-wasip2` or has a WASI shim |

## What this site builds

This site's worked example is one WIT contract, package `patterncatalyst:cargo@0.1.0` (the shipping and cargo domain this series uses throughout), implemented twice: once as a Rust component built with `cargo-component`, once as a Go component built with `wasm-tools`/`wit-bindgen-go`. The contract defines two interfaces, `booking` and `handling`, over a shared `types` interface carrying the domain's records (`booking`, `cargo`, `handling-event`, `itinerary`) and the `cargo-error` variant every function can return. That WIT contract gets a full walkthrough on its own; here it's enough to know that both language implementations target the same `cargo` world and are interchangeable from any caller's point of view, the same way the REST site's OpenAPI document and the gRPC site's `.proto` package define one contract two runtimes implement.

Those components run two ways. **wasmtime** is the standalone embedding: a single host process instantiating one or more components directly, the shape most of this site's early hands-on chapters build against, because it's the simplest way to see a component run. **wasmCloud** is the distributed layer on top: a lattice of hosts, each running wasmtime under the hood, that links components together declaratively and can move an instance from one host to another without redeploying it. wasmCloud gets introduced on its own later, and running both together in one deployment comes after that, because real systems built on server-side Wasm use wasmtime as the execution engine and wasmCloud (or something like it) as the thing deciding where and when that engine runs.

The deployment target is Kubernetes on two paths, covered with equal weight: minikube with the docker driver and containerd runtime for the default local path, and OpenShift Local (CRC) as the enterprise-platform appendix every container-related project in this series ends with. Both clusters run the same component artifacts; what changes between them is the platform wiring (ingress shape, image registry, the operator-managed add-ons), not the Wasm workload itself, which puts the portability claim from earlier in this chapter onto real infrastructure in Part 5.

## Container vs. Wasm component, concretely

Put a number against each of the three properties from earlier for the specific workload this site builds (a single `book-cargo` call against the shared cargo domain) and the comparison stops being abstract.

A containerized implementation of that same function, packaged as a minimal distroless image around a compiled Go or Rust binary, typically lands in the 20–80 MB range depending on the base image and static-linking choices, and a cold pod start (image pull aside, assuming the image is already cached on the node) runs several hundred milliseconds to a couple of seconds by the time the container runtime, the namespace setup, and the application's own startup code have all finished. The isolation boundary for that pod is the kernel: Kubernetes' pod security context can narrow the syscall surface with seccomp and drop capabilities, but the container still executes real instructions against a shared kernel, and a container escape (rare, but documented in the wild) reaches the node.

The same `book-cargo` function compiled as a Wasm component lands under 5 MB as a `.wasm` binary for either language, instantiates under wasmtime in low single-digit milliseconds once the module is cached, and never makes a syscall the host didn't explicitly grant: no filesystem access, no outbound socket, nothing beyond what the `cargo` world's WIT interface describes, unless a later chapter's WASI wiring adds that access explicitly. That's not a benchmark claim this chapter is asking to be taken on faith; measuring both shapes under wasmtime comes next, and the numbers here are the ballpark that measurement is expected to land in, not a substitute for it.

<div class="callout callout--safe"><p class="callout__title">Decision</p><p>Reach for a Wasm component over a container when the workload is short-lived or bursty enough that cold start and density matter, when the code is untrusted or third-party enough that a deny-by-default sandbox is worth the narrower default host access, or when the same logic has to run unmodified across architectures and clusters without a build matrix. Stay with a container when the workload holds long-lived state worth keeping warm, depends on a native library with no `wasm32-wasip2` path, or needs POSIX facilities (forking processes, raw device access, a real process table) that WASI Preview 2 does not expose. Most systems end up with both: this site's own deployment chapters run Wasm components as sidecars and ambassadors next to ordinary container workloads, not as a wholesale replacement for them.</p></div>
